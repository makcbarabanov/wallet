# RECEIPT_IMPLEMENTATION_PLAN.md

Receipt & Purchase Architecture Plan (AD-010)

## Цель

Добавить в Wallet поддержку чеков как нового источника данных.

Главный принцип:

**Чек показывает состав покупки. Банк показывает движение денег.**

Wallet не должен выбирать одно вместо другого:

- банк отвечает на вопрос: «сколько денег ушло со счёта»;
- чек отвечает на вопрос: «что именно было куплено»;
- Purchase (Покупка) связывает событие покупки и все его источники.

## Новая модель

### Purchase (Покупка)

Покупка — это событие: «Я совершил покупку в магазине в определённую дату».

Примеры: поход в Пятёрочку; покупка стройматериалов; покупка лекарств.

Purchase хранит:

- дату;
- магазин;
- общую сумму;
- связанные источники;
- связанные расходы.

### SourceOperation (источник)

Источник — это доказательство покупки.

Примеры: чек; банковская выписка; импорт; будущий API.

В AD-010:

```text
sourceOperation
    sourceType:
        receipt
        bank_statement
        ...
    данные источника
```

Одна Purchase может иметь несколько источников.

Пример:

```text
Purchase:
Пятёрочка
25.07.2026
2350 ₽

Источники:
✓ Фото чека
✓ Выписка банка
```

### Expense (расход)

Expense — это элемент статистики.

Именно Expense отвечает на вопросы: сколько потрачено на кофе; сколько ушло на продукты; сколько потрачено на стройку.

Пример — один чек:

```text
Покупка:
Пятёрочка 2350 ₽

Расходы:
Молоко 1000 ₽ · Продукты
Хлеб 1100 ₽ · Продукты
Жвачка 250 ₽ · Сладости
```

## Общие правила AD-010

1. **Чек детализирует покупку** — каждая позиция чека может стать отдельным Expense.
2. **Подтверждение обязательно** — Training mode; ИИ распознаёт и предлагает, не создаёт расходы сам.
3. **Создание расходов только через Gateway** — `createExpense()` → Ledger. Никаких обходных путей.
4. **Категория по товару, не по магазину.** Запрещено сводить чек к одной записи «Вимос → Материалы». В одном чеке позиции могут иметь разные категории.
5. **Обучение — на уровне позиции**, в **едином потоке** с выпиской и скрином (AD-010.1). Не отдельный пакетный экран чека. 100 позиций → до 100 вопросов обучения — это нормальная цена качества базы.
6. **Фото в Валете** для изображений идёт по пути чека (позиции), не по пути банковской выписки. PDF/CSV выписки — отдельно. После разбора позиции попадают в тот же tutor, что и импорт выписки.

## Запомнить правило Валета

- Чек — не расход. Чек — контейнер покупки.
- Каждая позиция — кандидат в отдельный расход.
- Категория определяется товаром.
- Банк = сколько ушло со счёта; чек = на что ушло.
- Выписка / скрин / чек — разные источники сырья, **один** процесс обучения пользователя.

## План реализации

### Волна 1 — Фундамент чеков (+ AD-010.1)

**Цель:** научить Wallet понимать чек как источник покупки и провести позиции через уже существующий двигатель обучения.

**Входит:**

- сущность Purchase;
- `sourceType = receipt`;
- загрузка изображения чека;
- LLM Vision анализ изображения;
- структурированные данные: магазин, дата, итог, позиции, количество, цена, предполагаемая категория;
- преобразование позиций → строки импорта → `startValetImportTutor` (полное имя товара на карточке);
- после подтверждения в tutor каждая позиция → отдельный Expense через `createExpense()`.

**Не входит / отменено:**

- отдельный пакетный экран «Подтвердить всё» для чека (концепция отменена, не чинить);
- банковские выписки; связывание чек↔банк; сложный дедуп; merchantId; Assistant; магазинные парсеры; камера; автоподтверждение.

### Волна 2 — Дружба с банком

Связать чек и банковскую операцию (банк первым / чек первым). Поиск совпадений на уровне Purchase; привязка источников; защита от двойного списания.

### Волна 3 — Обучение и интеллект

Обучение товарам, статистика ошибок, качество предложений, память решений, улучшение категорий.

## Не меняется

- **AD-009:** `createExpense()` — единственный вход; Training; пользователь решает.
- **AD-003:** банковский счёт — источник истины по деньгам на счетах.

## Промпт для Продагента — Волна 1

Работай только по этому заданию.

Не реализовывать: выписки; дедуп чек↔банк; merchantId; обучение товарам; Assistant; магазинные парсеры; камеру; автоматическое создание расходов.

### Цель

Фото чека → LLM анализ → предложение → подтверждение пользователя → `createExpense()`.

### Реализовать

1. **Purchase** — id, дата, магазин, сумма, связанные sourceOperation, связанные expenses. Старые расходы не ломать.
2. **sourceOperation** — `sourceType: "receipt"` + `receiptInfo { merchantRaw, date, totalAmount, items[], model, confidence }`.
3. **Загрузка изображения** — выбрать файл, отправить на анализ, получить результат. Без камеры.
4. **LLM Receipt Parser** — только структура, не создание расходов.
5. **Пакетное подтверждение** — список позиций, сумма, категория, правка, «Подтвердить всё». До подтверждения — ничего в Ledger.
6. **Создание расходов** — каждая позиция через `createExpense()`. Запрещены прямой `pushRow`, обход Gateway.

### Обязательные проверки

- Тест 1: чек с 3 позициями → 3 Expense.
- Тест 2: плохое фото → понятное сообщение + developer log, без падения.
- Тест 3: низкая уверенность → позиция остаётся предложением, решает пользователь.

### Критерий готовности

Изображение загружается; LLM возвращает структуру; пакет предложений виден; после подтверждения отдельные расходы через `createExpense()`; старый функционал не сломан.

**Конец задания. Кодировать только эту волну.**
