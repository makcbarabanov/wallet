## AD-009 — Единый ingest расходов и защита от дублей (фундамент)

**Дата:** 2026-07-24  
**Статус:** accepted + implemented (UI_BUILD 49 / schema 11, 2026-07-24)  
**Связанные:** AD-003 (сверка не подменяется дедупом), кейс NSP 21.07.26 / 10 511 ₽

### Контекст

Wallet принимает расходы многими каналами:

- PDF / Excel·CSV / скриншоты / буфер / ручной ввод / будущие интеграции.

Для пользователя это **один** процесс «добавить расход».  
Сейчас дедуп размазан по импорту (`planImportStatementRows`, fingerprints, soft/hard) и частично по `pushRow` (`findLedgerSoftDup`), при этом:

- импорт живёт в `importedOps` (+ ящик `drawerOps`, `rejectedOps`);
- подтверждённый расход — в `personal` / `business` с `opId`, **без** обязательной связи с исходной банковской строкой;
- `sourceOperationId` в коде **нет**;
- банковский operation id в fingerprint **не используется** (поля вроде bankOpId отсутствуют);
- ИИ/авто-классификация магазина **не** является проверкой уникальности.

**Кейс NSP:** в Ledger store=`NSP`, в выписке `Сервисный центр NSP`.  
`storesRelated` требует длину обеих сторон ≥ 5 для подстроки → короткий канон не матчится → строка снова в Разборе.  
«Верно» → новый `pushRow` + повторный debit счёта.

### Решение

1. **Единый конвейер ingest** для всех каналов:  
   `source operation` → (дедуп / решение пользователя) → `ledger expense` (personal|business) + debit счёта.

2. **Первичный слой — source operations** (логически; физически можно эволюционировать `importedOps` / ввести `sourceOps[]`):  
   каждая входящая операция получает стабильный **fingerprint** из:
   - дата (календарный день + время, если есть);
   - сумма (|amount| + знак/направление);
   - счёт / карта-hint, если известны;
   - магазин (канон + варианты имени);
   - назначение / comment / bank category;
   - **банковский ID**, если парсер его дал (иначе null).

3. **Подтверждённый расход** хранит связь:
   - `sourceOperationId` (или список id при объединении);
   - опционально копию `fingerprint` на момент подтверждения.

4. **Перед созданием расхода** (импорт, авто, ручной ввод, «Верно»):  
   проверка против source-слоя **и** Ledger.  
   При совпадении / сильном кандидате — **не создавать молча**.  
   UI: «Возможно, эта операция уже существует» →  
   - использовать существующую;  
   - создать новую (явный override + audit);  
   - объединить (связать source ↔ expense без второго debit).

5. **ИИ — помощник решения, не источник истины.**  
   Может ранжировать кандидатов и объяснять «почему похоже», но не подтверждает расход и не списывает счёт без пользователя.

6. **Сверка счетов (AD-003) не заменяется дедупом.**  
   Дедуп защищает от второго debit; сверка ловит дыры, если защита всё же обойдена.

7. **Обязательное подтверждение (текущий этап).**  
   Любой новый расход из любого канала проходит через подтверждение пользователя.  
   **Автосоздание расхода без вопроса — запрещено**, даже при высокой уверенности.  
   Причина: копим статистику точности (см. AD-009a и `WALLET_AI_LEARNING.md`) до отдельного AD о переходе в авто-режим.

### AD-009a — Два режима работы Wallet (управляются через Настройки)

| Режим | Поведение |
|-------|-----------|
| **Training mode** (текущий, активный) | любой новый расход требует подтверждения; ИИ предлагает, но не решает; все исправления пользователя доступны для обучения; считаем метрики качества |
| **Assistant mode** (будущий) | авто-принятие только выше установленного порога уверенности; сомнительные случаи всё равно к пользователю; всегда можно вернуть Training |

**Управление режимом — в Настройках Wallet:**

```text
AI режим:
  ○ Training (рекомендуемый)
  ○ Assistant (экспериментальный)
```

- Сейчас доступен **только Training**; Assistant включается пользователем отдельной галочкой **после** накопления достаточной статистики.
- Переход Training → Assistant — **не технический тумблер в коде, а отдельное архитектурное решение** после оценки метрик (§ `WALLET_AI_LEARNING.md`).
- Хранение: целевое `settings.aiMode: 'training' | 'assistant'` (default `'training'`); наличие галочки в UI не означает разрешение авто-режима без AD.

Детали метрик и разграничение «решает ИИ / решает пользователь» — в [WALLET_AI_LEARNING.md](./WALLET_AI_LEARNING.md).

### Каноническая форма source-слоя (утв. пользователем)

```text
sourceOperation:
  id
  sourceType         // pdf | excel | screenshot | manual | clipboard | api
  date
  amount
  accountId
  storeRaw
  storeNormalized
  comment
  fingerprint        // инструмент поиска кандидатов, НЕ уникальный ключ
  bankId?            // если парсер дал (иначе null) → признак Exact-совпадения
  status             // queued | linked | rejected | merged
  duplicateResolution // none | linked_existing | created_new | merged | allowed_duplicate

expense (personal | business):
  opId
  sourceOperationId   // «этот расход появился из вот этой исходной операции»
  ...
```

Принцип: **идём от архитектуры входящего слоя, а не от «поиска похожего расхода»**.  
Расход всегда помнит свой источник → перестаём гадать.

### Причина

Иначе каждый новый канал (скрин, Excel, интеграция) снова изобретёт свой дедуп, и кейсы вроде NSP будут повторяться с порчей сверки.

### Последствия (направление реализации — не код этого AD)

| Сейчас | Цель |
|--------|------|
| `importedOps` = очередь Разбора | Явный source-слой (+ статусы: queued / linked / rejected / merged) |
| `personal`/`business` только `opId` | + `sourceOperationId?`, `fingerprint?` |
| Hard/soft только при CSV-импорте | Тот же матчер на **всех** входах в `pushRow` / confirm |
| `storesRelated` режет короткие имена | Отдельное правило матчинга магазинов (токены / alias / безопасная подстрока) + AD-правка при смене эвристики |
| Soft-dup → skip или Разбор (исторически менялось) | Единая политика: кандидат → диалог, не тихий второй расход |

**Не в этом AD:** полная история source, отдельная БД, обязательный bank id от всех банков.

**Порядок внедрения (предложение):**  
спроектировать матчер → AD-уточнение эвристик магазина при необходимости → schema + `sourceOperation` / `sourceOperationId` → единый gate перед `pushRow` → UI диалога → каналы по очереди.  
Фазы UI (Настройки, кнопки Личный/Бизнес) не отменяют этот фундамент: любой новый «добавить расход» обязан пройти gate **и подтверждение** (п.7).

### Обязательный тест: кейс NSP

Регрессионный тест (добавить при реализации, напр. `data/fixtures/tbank/05_nsp_soft_store.csv` + проверка матчера):

```text
Существует в Ledger:
  21.07.26 · NSP · 10 511 ₽ · Т кредитка

Вход (любой канал):
  21.07.26 · Сервисный центр NSP · 10 511 ₽ · Т кредитка

Ожидаемо: Wallet НЕ создаёт молча, а показывает
  «Найдена возможная существующая операция. Совпадение:
     дата ✓ · сумма ✓ · счёт ✓ · магазин похож ✓»
  и даёт выбор: использовать существующую / создать новую / объединить.
```

Требование: не «починить только NSP», а покрыть класс «короткий канон vs длинное имя банка» тестом.

### Закрытые уточнения (решения пользователя, 2026-07-24)

1. **sourceOperation: importedOps или отдельный массив?**  
   Пока **не** делать отдельный массив. `importedOps` уже играет роль входящего слоя →  
   эволюционирует в `sourceOperation` (добавляем недостающие поля), новые каналы используют тот же формат.

   - **Weak candidate** — только часть признаков.

   `none | linked_existing | created_new | merged | allowed_duplicate`.  
   Причина: нужна аналитика — сколько раз ИИ ошибся, сколько реальных дублей создал пользователь, сколько объединяли.

## AD-010 — Покупка, чеки и несколько источников (модель данных)

**Дата:** 2026-07-26  
**Статус:** accepted (решение зафиксировано; код ещё не начат)  
**Связанные:** AD-009 / AD-009a (единый шлюз и Training), AD-003 (сверка счетов)

### Контекст

После стабилизации v58 следующий большой сдвиг — чеки. Чек и банковская выписка отвечают на **разные** вопросы:

- банк: «сколько денег ушло со счёта?»
- чек: «на что именно ушли деньги?»

Пользовательская цель: статистика потребления (кофе за год, лекарства и т.д.). Поэтому **загрузка чека = сигнал детализации**: позиции становятся отдельными расходами, без вопроса «разбить или оставить одной суммой».

Старая связка «источник → один расход» недостаточна: один платёж банка может соответствовать нескольким расходам по позициям чека.

### Решение

1. **Обязательная сущность «Покупка» (`Purchase`).**  
   Промежуточный объект между доказательствами и расходами:

   ```text
   Purchase
     ├── sources[]     // банк, чек, позже email / API / …
     └── expenses[]    // один или несколько расходов
   ```

   Покупка создаётся **всегда**:
   - только банк → покупка без детализации (один общий расход);
   - только чек → покупка с детализацией (расходы по позициям; счёт может быть неизвестен);
   - банк + чек → одна покупка с двумя источниками.

2. **Источники истины (строго):**
   - **Банковский источник** — источник истины для **движения денег по счетам** (сколько реально списано, с какого счёта).
   - **Чек** — источник истины для **состава покупки** (позиции, названия товаров, детализация).
   - Чек не «побеждает» банк по деньгам при скидках/бонусах/округлении.

3. **Чек → отдельные расходы.**  
   Каждая позиция чека после подтверждения пользователя создаёт отдельный расход через существующий `createExpense()` (AD-009).  
   Дата, магазин и прочие реквизиты чека копируются на каждую позицию.  
   Категории предлагает ИИ; в Training mode каждая позиция подтверждается пользователем **в том же потоке обучения, что и выписка** (AD-010.1) — не отдельным «пакетным экраном чека».

4. **Банк без чека.**  
   Создаётся Покупка с одним общим расходом (как сейчас по смыслу). Детализации нет, пока не появится чек.

5. **Когда чек приходит к уже существующей банковской покупке.**  
   Общий расход **заменяется** детализацией (позиции), факт оплаты банка на Покупке сохраняется. Визуально и в расчётах потребления побеждают позиции; банковский источник не стирается из данных (нужен для повторного импорта выписки и сверки).

6. **Дедуп на уровне Покупки**, не отдельных позиций.  
   Строка банка «Пятёрочка −2350» ищется среди Покупок с той же суммой/датой/магазином — не сравнивается с «Молоко 1000».  
   При совпадении: второй набор расходов не создаём; к Покупке добавляем источник.

7. **Расхождение сумм чека и банка.**  
   Если |итог чека − сумма банка| больше допуска — в Training спросить («это одна операция?»), не склеивать молча.  
   Отчёты «ушло со счёта» опираются на банк; «сколько на кофе» — на позиции.

8. **ИИ — парсер и помощник, не бухгалтер.**  
   LLM извлекает структуру чека и предлагает категории. Автосоздание расходов без подтверждения запрещено (AD-009a).  
   Отдельные парсеры под каждый магазин — запрещены.

9. **Честный отказ.**  
   Если чек / файл не распознан — **модалка** («что произошло» + «что можно сделать»), без «тихого» тоста.  
   Та же ошибка пишется в существующий журнал `/logs` через `reportUserError()` → Valet critical (`user_error`), без второго журнала.  
   В лог нельзя класть фото, полный текст чека, позиции, суммы, токены и `.env`.  
   Частичное распознавание: «распознано N из M» → Продолжить (N идут в обычный Разбор) / Отмена.  
   Сбой логирования не должен скрывать окно ошибки.

10. **Позиция чека = обычный расход (ед. / кол-во / цена / стоимость).**  
    `price` = цена за единицу, `qty` = купленное количество, `amount` = сумма строки, `unit` = кг/л/шт/….  
    Инвариант: любое нарушение `price × qty ≈ amount` (с допуском округления магазина) → `amountStatus=doubt` и **вопрос пользователю в текущем Разборе**.  
    Валет **не** исправляет сомнения автоматически и не подставляет «похожее» число в расход.  
    Поля `unit`/`qty`/`price`/`amount` сохраняются до `createExpense()` / `makeRow`.

### AD-010.1 — Единый интерфейс обучения расходов

**Дата:** 2026-07-26  
**Статус:** accepted  
**Связанные:** AD-010, AD-009 / AD-009a

#### Контекст

Отдельный пакетный экран подтверждения чека оптимизировал скорость кликов, но обрезал названия товаров и оторвал чек от уже работающего потока обучения выписки. Пользователь готов отвечать на N вопросов по N позициям — это цена обучения Валета.

#### Решение

1. **Не создавать отдельный UX для чеков** (и не «чинить» пакетный экран — концепция отменена).

2. Независимо от источника:
   - банковская выписка;
   - скриншот банка;
   - чек;
   - PDF / текст / будущий голос;

   после распознавания данные попадают в **единый поток обучения** — **карточки Валета** (тот же экран Разбора, где человек отвечает по одной операции).

3. **Один интерфейс подтверждения.**  
   Продолжение незавершённого разбора — только в том же tutor-интерфейсе, на котором остановились.  
   Запрещено открывать «другой» экран (старый список групп, пакетное окно чека, отдельная форма под тип источника).

4. Каждый расход показывается отдельно. Обязательно видно:
   - название расхода (для чека — **полное имя товара**);
   - сумму;
   - дату;
   - магазин / контрагента;
   - текущую классификацию;
   - возможность исправить.

5. **Инвариант: одна карточка Валета = один расход.**  
   Запрещено: агрегация очереди в «группы», заголовки «Группа N из M», кнопки «Верно · все N» / массовое назначение нескольких расходов одним действием.  
   Очередь: `reviewItems → buildValetTutorItems → valetTutor.items` без `groupValetTutorItems`.  
   Технические массивы внутри карточки (`ops`) допустимы только как обёртка ровно одной операции (`ops.length === 1`), не как единица UX.

6. Чек даёт список позиций и детализацию покупки, но **не создаёт отдельный процесс подтверждения**. Позиции чека превращаются в обычные строки импорта (`sourceType: receipt`) и идут в тот же tutor, что CSV/скрин.

7. Под капотом сохраняется AD-010: Покупка + источники + расходы через `createExpense()`. Меняется только UX-вход, не модель данных.

#### Порядок реализации

Волна 1 (уточнение): убрать пакетный экран → `receipt → import rows → startValetImportTutor`.  
Волна 2/3 без изменений по смыслу AD-010.

### AD-010.2 — Политика дублей: единый поиск существующих записей

**Дата:** 2026-07-26  
**Статус:** accepted (уточнено после AD-011)  
**Связанные:** AD-010, AD-010.1, AD-011, AD-009

#### Контекст

Повторная загрузка того же чека молча создавала вторые расходы. Отдельная фраза «этот чек уже разбирали» — **запрещённый** уровень абстракции: пользователь не должен думать «чек vs выписка».

#### Решение

1. **Один механизм для любого источника.**  
   После распознавания: найти уже существующие записи → в Разбор попадают **только новые**.  
   Возможные совпадения спрашиваются **до** обучения (Отмена / Добавить), не после «Верно».  
   Сообщение однотипное: «Найдено N новых записей» (не «чек обработан» / «выписка загружена»).

2. **Exact / Strong — уверенный дубль (пропускаем без Разбора):**  
   - номер чека / `fiscalId`, если есть;  
   - иначе для **позиции чека**: дата + сумма + имя товара (с учётом OCR-дрейфа); магазин для позиции чека **не обязателен**;  
   - для **банка**: дата + \|сумма\| + (похожесть магазина **ИЛИ** идентификатор phone/card/account/contract **ИЛИ** счёт/карта);  
   - **подтверждённая связь reconciliation** (`reconciliationLinks`): после ответа «Да, это одна запись» в Уточнении — при следующем импорте **silent skip** (не merchant learning).  
   - **Запрещено:** `bank.comment` → `productName` → товарная ветка (карта / MCC / служебное описание — не товар).  
   - **Запрещено:** считать дублем только по дню + сумме без третьего сигнала (такие случаи → possible / Уточнение, не silent skip).  
   - Наличие `expense` в Ledger само по себе **не** делает банковский вход товарной позицией.

3. **Weak / similar (сомнение → Уточнение ДО обучения):**  
   та же дата, похожее имя товара, сумма близка (например 37 vs 38 ₽).  
   Кнопки: **Да, это одна запись** (связь + skip) | **Нет, это новый расход** (в Разбор) | **Отмена**.  
   Навигация ← → по списку уточнений.  
   Для банка: день+сумма без магазина/id → possible (Уточнение), не confident skip.

4. **Частично обработанный источник:**  
   из 10 позиций 5 уже есть → «Найдено 5 новых» → Разбор только по новым.

5. При `createExpense()` дедуп **не отключать** (последний щит).  
   Если пользователь впервые узнал о дубле только там — сломан этап до обучения.

#### Явно не входит

- Soft-delete история для дедупа (отдельная волна).  
- Банк↔чек в одну Purchase (волна 2 / Purchase reconciliation).  
- Фоновая проверка при открытии Валета.

## AD-011 — Unified Source Processing

**Дата:** 2026-07-26  
**Статус:** accepted  
**Связанные:** AD-010 (Purchase), AD-010.1 (единый Разбор), AD-010.2 (дедуп), AD-009 / AD-009a

### Формулировка

Все источники расходов (банк, чек, скрин, PDF, текст, будущие каналы) проходят **единый конвейер**:

```text
Источник → распознавание → нормализация → поиск существующих
  → новые / сомнительные предложения → Разбор → подтверждение → createExpense() → Ledger
```

Разница источников существует только **внутри данных** (`sourceType`, поля чека/банка), не в пользовательском сценарии и не в отдельном коде записи расходов.

### Запрещено

- Отдельный путь записи расходов для нового типа источника.  
- Отдельный экран «подтверждение чека / выписки / голоса».  
- Сообщения вида «этот чек уже обработан» / «эта выписка уже загружена» как особый UX.
- Переключатели «Авто / Спрашивать» по магазину в Разборе, пока активен Training mode: подтверждает всегда пользователь (AD-009a), поэтому такой тумблер только путает. Память магазина остаётся, но влияет лишь на подсказку.
- Показ незавершённого хвоста Разбора без явного согласия: если очередь осталась с прошлого раза, карточки скрыты до ответа «Да» на «Продолжить?».
- При «Продолжить» — открывать **не** тот интерфейс, на котором шло обучение (карточки Валета). Старый список групп с кнопками вроде «Неучёл» — не продолжение разбора, а другой UX; для продолжения импорта запрещён.

### Разрешено

- Разные парсеры/OCR на входе.  
- Разный текст кнопок при сомнении (чек: Отмена/Добавить; банк: расширенный набор), при **одной** логике дедупа.

### Явно не входит в AD-010 (позже)

- Полная реализация волн кода (см. `RECEIPT_IMPLEMENTATION_PLAN.md`).
- Авто-линк без вопроса (Assistant).
- Умные возвраты товара (связь заложить, логику — отдельно).
- `merchantId`-миграция истории.
- Receipt Learning как отдельный продуктовый слой обучения по товарам (карта / roadmap).

### Порядок реализации (после AD, до массового кода)

1. `RECEIPT_IMPLEMENTATION_PLAN.md` (проектный план волн).  
2. Волна 1: `Purchase` + разбор чека + **единый tutor** + `createExpense()`.  
3. Волна 2: дружба с выпиской (дедуп по Покупке, замена общего расхода детализацией, расхождение сумм).  
4. Волна 3: обучение по товарам и статистика потребления.
